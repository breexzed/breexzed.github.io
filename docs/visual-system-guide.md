# BREEXZED visual asset system

This document describes the exact visual system used for the estate’s node imagery and how to reproduce it from scratch without depending on custom runtime logic. It is designed so another agent can rebuild the setup faithfully, including the fast-loading and card-vs-detail variant pattern.

## Goal

The visual system is intentionally minimal, editorial, and fast:

- Use lightweight SVG assets, not raster-heavy JPG/PNG
- Keep the design language consistent: dark atmospheric background, geometric overlays, high-contrast lines, soft gradients
- Provide two variants per node:
  - `thumbnail`: compact crop for card/grid previews
  - `visual`: wider, more open composition for the detail/hero view
- Keep the metadata source of truth in the markdown frontmatter, so rebuilds are deterministic

## Why this pattern works

The estate uses a static topology whose source data lives in Markdown files under `nodes/`. The runtime consumes `thumbnail` and `visual` values from the node frontmatter and renders the image in the relevant surface.

This gives us:

- fast page loads: SVG is tiny and crisp
- consistent presentation across cards and node pages
- a reversible design system: no hard-coded image layout in the app logic
- content-first asset management: every image is attached to a node, not a separate ad hoc gallery

## File architecture

Relevant repository paths:

- `nodes/projects/*.md`
- `nodes/concepts/*.md`
- `nodes/articulations/*.md`
- `public/assets/visuals/` (generated by build)
- `scripts/copy-assets.js`
- `scripts/build-topology.js`

The build pipeline copies all node assets into `public/assets/visuals` and rewrites relative markdown asset paths to public URLs automatically.

## Required conventions

### 1. Create both asset variants

For each node that should have a visual, create two files: a compact thumbnail and a broader hero image.

Use this naming pattern:

- `node_id-thumb.svg`
- `node_id-visual.svg`

Example:

- `estate_lab-thumb.svg`
- `estate_lab-visual.svg`

The node ID should match the Markdown `id` value in the frontmatter. The build system expects the final path to resolve cleanly from the source Markdown file.

### 2. Add frontmatter metadata

Add both fields to the node’s markdown frontmatter:

```yaml
---
id: estate_lab
title: Estate Lab
label: project
formula: living -> systems -> prototypes
depth: 1
parent: root
type: projects
status: published
domain: systems
thumbnail: ./estate_lab-thumb.svg
visual: ./estate_lab-visual.svg
images:
  - ./estate_lab-thumb.svg
  - ./estate_lab-visual.svg
links:
  - label: Case study
    href: https://example.com/estate-lab
  - label: Repository
    href: https://github.com/example/estate-lab
tags:
  - living
  - practice
  - systems
---
```

Important rules:

- Prefer relative file paths from the Markdown file itself
- Keep names lowercase and use underscores for IDs and filenames
- Use SVG, not PNG/JPG, whenever possible for editability and speed
- If a node has no image, leave both fields unset
- `images` and `links` are intentionally optional and share the same static build flow as `visual`/`thumbnail`

### 3. Reuse the same pattern across any node type

This works for:

- projects
- concepts
- articulations
- signals
- trails
- any future node type

The interface is intentionally generic: a node can carry a primary `visual`, a compact `thumbnail`, a gallery list in `images`, and a simple list of reference links in `links`.

### 3. Keep the visual language coherent

Use this formula for the visual treatment:

- dark base background
- cool atmospheric blue / plum / bronze gradients depending on domain
- simple geometric rings, paths, panels, and nodes
- sparse but deliberate linework
- soft glow, clipped to shape with minimal noise
- no heavy photography, no complex textures

This is an editorial, diagrammatic system: not illustration, not collage, not photo-based.

## Reproduction workflow

### Step 1: Decide which nodes need visuals

Only attach visuals to nodes that should become legible in the estate UI. The general pattern is:

- projects
- concepts
- articulations

For this site, the intended nodes are:

- `estate_lab`
- `systems_as_world`
- `knowing_and_knowledge`
- `being_in_the_world`
- `world_as_systems`
- `knowledge_in_motion`
- `constraints_and_becoming`

### Step 2: Create the asset directory structure

```bash
mkdir -p nodes/projects nodes/concepts nodes/articulations
```

### Step 3: Generate the SVGs

A single SVG pair is enough. Use simple geometry and gradients.

```svg
<svg width="1200" height="800" viewBox="0 0 1200 800" fill="none" xmlns="http://www.w3.org/2000/svg">
  <defs>
    <linearGradient id="bg" x1="120" y1="60" x2="1080" y2="760" gradientUnits="userSpaceOnUse">
      <stop stop-color="#0B1426"/>
      <stop offset="1" stop-color="#131B2A"/>
    </linearGradient>
    <linearGradient id="glow" x1="280" y1="150" x2="880" y2="560" gradientUnits="userSpaceOnUse">
      <stop stop-color="#D9F4FF"/>
      <stop offset="1" stop-color="#6DE1D4"/>
    </linearGradient>
  </defs>
  <rect width="1200" height="800" fill="url(#bg)"/>
  <circle cx="317" cy="336" r="156" fill="#0E1E2F" stroke="#E8F0FF" stroke-opacity="0.38"/>
  <circle cx="317" cy="336" r="102" fill="url(#glow)" fill-opacity="0.9"/>
  <circle cx="806" cy="396" r="170" fill="#101C2E" stroke="#E8F0FF" stroke-opacity="0.30"/>
  <circle cx="806" cy="396" r="88" fill="url(#glow)" fill-opacity="0.7"/>
  <path d="M250 530L500 246L758 392L980 238" stroke="#EAF6FF" stroke-width="4" stroke-linecap="round" stroke-linejoin="round"/>
  <rect x="470" y="462" width="230" height="132" rx="18" fill="#0B1725" stroke="#EAF6FF" stroke-opacity="0.28"/>
</svg>
```

Then create a broader hero version with a wider canvas such as `1600x1000` and more breathing room.

### Step 4: Add the asset references to node frontmatter

For each file, add the `thumbnail` and `visual` fields exactly as shown above.

### Step 5: Rebuild the topology and copy the assets

Use the existing project script:

```bash
npm run build
```

This runs:

- `build:topology`
- `copy:assets`
- `build:search`
- then `vite build`

### Step 6: Validate results

Check the generated HTML or run the app preview:

```bash
npm run dev -- --host 0.0.0.0
```

Then open the site and verify:

- cards show the compact thumbnail
- node pages show the larger visual
- no missing images appear
- no broken URLs or relative path issues exist

## Edge cases and failure modes

### Missing asset path

If the asset path is wrong:

- the build still completes, but the image may not show in the UI
- the node card will silently fall back to text if `visual` or `thumbnail` are missing

Audit with:

```bash
grep -R "thumbnail\|visual" nodes
```

### Wrong filename casing

The repo is case-sensitive on Linux. Use exact lowercase names and match the frontmatter path to the actual file. If there is a mismatch, the asset path will fail at runtime.

### Using raster formats unnecessarily

JPG and PNG hurt performance. This system intentionally uses SVG to maintain:

- smaller files
- instant rendering
- no heavy network overhead
- crisp scaling at any size

### Overloading the detail view with a large image

The node page can show a large visual, but the layout still needs to remain editorial and calm. Keep the image within the reading surface and avoid visual noise.

### Source arrays and copied assets

The `copy-assets.js` script automatically scans `nodes/**/*.{png,jpg,jpeg,gif,svg,webp,avif}` and rewrites asset paths when the site is built. Do not manually edit the generated `public/data/topology.json` by hand unless you are deliberately testing the output.

## Best practices for future agents

- Always prefer SVG for this estate visual system
- Keep the geometry abstract and calm
- Use same background treatment across all nodes to preserve the “estate” identity
- Keep image reading performant by not embedding large raster data
- Attach thumbnails and visuals at the node content level rather than in UI-only code
- Treat the Markdown frontmatter as the canonical source of the asset references

## Summary

The visual system is a content-first, lightweight, editorial layer that makes the estate feel coherent without making the app heavy. The crucial ingredients are:

- node-level metadata
- SVG variants
- relative asset paths
- a build pipeline that copies assets into `public/assets/visuals`
- consistent geometric styling

If you follow this recipe exactly, the estate image system is fully reproducible and easy to extend.
